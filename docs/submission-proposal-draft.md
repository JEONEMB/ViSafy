# 2026 금융 AI Challenge 공모전 기획서 (작성안)

양식 [첨부1]의 7개 항목 순서 그대로 작성했다. 각 절을 양식 표의 해당 칸에 옮긴 뒤 PDF로 변환한다.

> **팀명·구성원 성명은 등록된 값으로 직접 채운다.** 이 문서에는 비워 두었다.

---

## 1. 서비스 명칭

**SSAFIN (싸핀) — 외국인을 위한 공식정보 기반 금융정착 AI Agent**

> 부제로 쓸 한 줄: "은행 앞까지가 아니라, 창구 안까지 함께 가는 AI"

---

## 2. 아이디어 기획 핵심내용 (요약)

- **대상**: 국내 체류 외국인 (특히 E-9·E-7 등 취업 체류자격 보유자)
- **채널**: 모바일 웹 + **오프라인 영업점 창구** — 창구를 결과물이 소비되는 접점으로 설계
- **핵심 문제**: 외국인은 상품을 찾아내도 **은행 창구에서 실행에 실패**한다. 서류 누락으로 헛걸음하고, 은행원의 되물음에 대화가 멈춘다
- **해결**: 공식 자료로 조건을 판정하고, 그 결과를 **창구에서 바로 쓸 수 있는 산출물**로 전환
  - 공식 Source → 생성형 AI 조건 후보 제안 → **원문 대조 검증** → 사람 검수 → Rule Engine 결정론적 판정
  - 결과물 = **「창구 준비 패킷」** : 챙길 서류 · 창구용 한국어 문장 · **은행원 예상 질문과 답변** · 신청 절차 · 공식 근거
- **안전 원칙**: 생성형 AI는 조건 후보를 **제안**할 뿐 **자격을 결정하지 않는다.** 원문 대조 검증과 사람 승인을 통과한 조건만 판정에 사용
- **모르는 것은 모른다고 답한다**: 공개 자료에 없는 조건은 `UNKNOWN`으로 남기고, 은행에 확인할 항목으로 구조화
- **6개 언어** (한국어·영어·베트남어·중국어·일본어·태국어) 전면 지원 — 판정 메시지·서류 안내·창구 대사까지 포함
- **구현 완료**: 공개 HTTPS URL에서 동작하는 MVP, 4개 금융기관 11개 상품, 자동 테스트 168건

## 3. 문제 정의 및 제안 배경

### 3-1. 시장은 이미 열렸고, 금융권은 대규모로 투자하고 있다

| 지표 | 수치 | 시점 |
| --- | --- | --- |
| 5대 은행 외국인 고객 | **688만 2,187명** | 2026년 6월 말 |
| 5대 은행 외국인 예금 잔액 | **25조 2,657억 원** | 2026년 6월 말 |
| 외국인 특화 일요영업점 | 하나 17 · KB 8 · 우리 4 · 신한 3 · 농협 3곳 | 2026년 |

각 은행의 최근 행보도 뚜렷하다.

- **하나은행**: 외국인 고객 257만 명(전체의 37.4%)·예금 8조 3,370억 원. 2026년 1월 전용 플랫폼 `Hana EZ` 고도화 — 실명확인 등록, 여권번호 변경, 공과금 납부, 각종 증명서 발급을 비대면화
- **KB국민은행**: 2026년 5월 외국인 전용 `Global Star 적금` 출시(최고 연 5.5%). 해외송금 `KB 퀵 센드` 지원국가를 5개국 → 47개국 확대
- **신한은행**: 16개 언어 지원 플랫폼 `쏠글로벌`, `SOL글로벌론`(최대 5,000만 원), 외국인 중심 영업점 확대
- **우리은행**: `우리WON글로벌`, 유학생 커뮤니티 제휴
- **NH농협은행**: `NH K-외국인 신용대출`(최대 3,000만 원)

**즉, 공급자 측의 의지와 투자는 충분하다.**

### 3-2. 그런데 정작 고객은 창구에서 막힌다

같은 시기 보도는 한계도 함께 지적한다. **5대 은행의 외국인 전용 상품은 20개 수준이고, 입출금통장·적금 등 기초 상품에 집중돼 있다.**

문제는 상품 수가 아니라 **고객이 그 상품에 도달하지 못한다는 점**이다. 국내 체류 외국인이 겪는 장벽은 두 단계다.

**① 정보 접근 장벽**

- 상품 조건·필요서류·신청 절차의 원문이 한국어로만 제공된다
- 번역기를 써도 "실명확인증표", "거래외국환 지정은행", "보증보험증권" 같은 금융 용어는 의미가 전달되지 않는다
- 은행 앱이 다국어를 지원해도, **가입 조건의 근거가 되는 상품설명서·약관은 여전히 한국어**다

**② 창구 실행 장벽 — 기존 서비스가 다루지 않는 영역**

정보를 얻어 은행에 가도 실제로는 이렇게 실패한다.

- 서류를 하나 빠뜨려 헛걸음한다. 어떤 서류가 **내 상황에** 필요한지 사전에 알 수 없기 때문이다
- 준비한 말은 화면으로 보여줄 수 있다. 그러나 **은행원이 되물으면 대화가 멈춘다.** "외국인등록증 있으세요?", "어떤 용도로 사용하실 건가요?" 같은 질문에 답하지 못해 절차가 중단된다
- 창구에서 겪는 진짜 어려움은 **말하기가 아니라 듣기**다

기존 서비스는 ①만 다룬다. 그래서 아무리 잘 만들어도 **"은행 사이트로 보내주는 번역기"**에 머문다. 실사용자 검증에서도 같은 지적을 받았고, 그것이 이 서비스의 설계를 바꾼 결정적 피드백이었다.

### 3-3. 고객과 채널을 이렇게 선택한 이유

| 선택 | 이유 |
| --- | --- |
| **국내 체류 외국인 (취업 체류자격 중심)** | 688만 명 규모에 예금 25조 원이 형성돼 있으나, 체류자격에 따라 가입 가능 여부가 달라져 **판단 난이도가 가장 높은 집단**이다. 잘못된 안내의 비용도 가장 크다 |
| **모바일 웹 + 오프라인 영업점 창구** | 외국인 대상 상품의 상당수가 **실명확인 의무 때문에 영업점 방문을 요구**한다. 온라인만 다루면 실제 실행 지점을 비워 두게 된다. 그래서 **창구를 결과물이 소비되는 최종 접점으로 설계**했다 |
| **앱이 아닌 웹** | 설치·회원가입 없이 즉시 접근. 체류 초기 외국인에게 앱 설치와 본인인증은 그 자체가 장벽이다 |

## 4. 서비스 컨셉 및 차별성

### 4-1. 핵심 컨셉

> **"은행 앞까지가 아니라, 창구 안까지."**

SSAFIN은 상품을 추천하고 끝내지 않는다. **사용자가 은행 창구에 도착했을 때 손에 무엇을 들고 있는가**를 설계한다.

마지막 한 걸음이 은행인 것은 바꿀 수 없다. 실명확인 의무 때문에 계좌 개설은 은행이 해야 한다. **바꿀 수 있는 것은 그 순간 사용자가 무장하고 있는가다.** 인간 재무설계사도 "이 서류 들고 은행 가세요"로 끝나지만 아무도 그를 리다이렉트 서비스라 부르지 않는다. 분석하고, 서류를 챙겨주고, 무슨 말을 할지 알려줬기 때문이다.

### 4-2. 기존 금융 앱 대비 차별성

| 구분 | 기존 은행 앱·번역 서비스 | SSAFIN |
| --- | --- | --- |
| **근거** | 앱 화면 문구를 번역 / LLM이 생성 | **공식 원문 인용 + 페이지 위치**를 판정마다 표시 |
| **판정 방식** | 가입 가능성·확률·점수 | **결정론적 규칙 엔진**. 충족 / 미충족 / 은행확인 필요 / 불명 **4분류** |
| **모르는 것** | 그럴듯하게 생성하거나 침묵 | **`UNKNOWN`으로 명시**하고 은행에 확인할 항목으로 구조화 |
| **최종 산출물** | 상품 상세 페이지 링크 | **「창구 준비 패킷」** — 인쇄·모바일 열람 가능한 문서 |
| **창구 대응** | 없음 | **은행원 예상 질문 + 상황별 답변**을 한국어·모국어 병기 |
| **다국어 범위** | 화면 문구 위주, 미지원 언어는 영어 대체 | 판정 메시지·서류명·신청절차·창구 대사까지 **6개 언어 전면** |
| **AI 권한** | LLM이 답변을 생성 | **LLM은 자격을 결정할 권한이 없음.** 제안 → 검증 → 사람 승인 |

### 4-3. 독창적 기능 — 「창구 준비 패킷」

사용자가 진단을 마치면 아래 한 장이 생성된다. 인쇄해서 들고 가거나 휴대폰으로 연다.

```
1. 챙겨갈 서류      공식필수 / 상황별 / 은행확인 3분류 체크박스
                   Residence card (외국인등록증) ← 번역 옆에 한국어 병기
                   관공서·창구에서 한국어 이름으로 요청해야 하므로

2. 창구에서 보여줄 문장   한국어 크게 + 모국어 번역
                   [은행원에게 보여주기] → 전체화면 한국어

3. 은행원과 주고받을 대화
   내가 확인 요청할 것    "제 신분증으로 실명확인이 가능한지 확인해 주시겠어요?"
   은행원이 물어볼 것     "외국인등록증 있으세요?"  (+ 모국어 번역)
     내 답변 선택지       "네, 여기 있습니다." / "아니요, 여권만 있습니다."

4. 공식 신청 절차    STEP + 채널
5. 공식 근거        Source URL + 확인일
```

**설계 원칙 — 사용자를 대신해 주장하지 않는다.**
답변 문장은 **사용자가 입력한 사실을 말하거나 질문만** 할 수 있다. "저는 조건을 충족합니다" 같은 문장은 **어떤 언어로도 생성하지 않는다.** 자격 판단은 은행의 권한이고, 외국인 입으로 대신 주장하게 만드는 것은 위험하기 때문이다. 이 제약은 자동 테스트로 강제된다.

## 5. 활용 데이터 및 생성형 AI 모델 적용 방안

### 5-1. 활용 데이터

| 데이터 | 내용 | 수집·활용 방안 |
| --- | --- | --- |
| **공식 금융 Source** | 은행 공식 상품 상세페이지, 상품설명서, 약관 | **공식 도메인 allowlist**(17개)에 등록된 출처만 수집. 원문 Snapshot과 **SHA-256 해시**를 저장해 변경을 감지 |
| **상품 Rule** | 체류자격, 국내 거주기간, 급여소득 기간, 최소 납입액 등 | 공식 Snapshot에서 추출·검수해 구조화. 각 Rule에 **원문 인용문·페이지·섹션**을 연결 |
| **필요서류·신청절차** | 공식 필수 / 조건부 / 은행확인 3분류, 신청 STEP과 채널 | 공식 자료에 명시된 것만 등록. 근거가 없으면 등록하지 않는다 |
| **임시 프로필** | 국적, 체류자격, 체류기간, 소득, 준비상태 | **여권번호·외국인등록번호·계좌번호는 수집하지 않는다.** 24시간 후 자동 만료 |

현재 **4개 금융기관 11개 상품**이 검수를 통과해 등록되어 있다. 수를 늘리기 위해 검수되지 않은 상품을 넣지 않는 것이 이 서비스의 전제다.

### 5-2. 생성형 AI 모델의 역할 — 4가지

**적용 모델**: OpenAI Responses API (Structured Output, JSON Schema strict)
**임베딩**: FastEmbed `intfloat/multilingual-e5-small` (384차원 다국어) + ChromaDB

#### ① 공식 문서에서 조건 후보 제안 — 그리고 기계적 검증

가장 중요한 적용 지점이다. 생성형 AI가 공식 문서를 읽고 Rule 후보를 제안하되, **제안이 곧 채택은 아니다.**

```
공식 Snapshot
  → [LLM] 조건 후보 제안 (rule_key, operator, value, 원문 인용)
  → [결정론적 검증기] 아래를 모두 통과해야 저장
       · 허용된 rule_key 목록에 있는가
       · 인용문이 원문에 문자 그대로 존재하는가
       · 숫자·비자코드가 인용문 안에 실제로 등장하는가
       · 값의 형식이 Rule Engine이 비교 가능한 형태인가
  → [사람] 검수 승인
  → Rule Engine 판정에 사용
```

검증에 실패한 제안은 **저장되지 않고 폐기**된다. 실제 개발 과정에서 LLM이 `RESIDENT_STATUS = "국내 거주자"`라는 값을 제안한 사례가 있었는데, Rule Engine은 `RESIDENT`/`NON_RESIDENT`로 비교하므로 그대로 승인됐다면 조용한 오판정으로 이어졌을 것이다. 검증기가 이를 차단했다.

> **이 구조가 이 프로젝트의 핵심 주장이다.** 생성형 AI를 쓰되, AI의 출력이 사용자 판정에 직접 도달하지 못하게 만든다.

#### ② 쉬운 설명 · 다음 행동 · 은행 문의문 생성

판정이 끝난 결과를 사용자 언어로 설명한다. 이때 **구조화된 입력만** 사용한다.

- 비자코드, 잔여 개월, 체류 개월, 조건 수는 Backend가 넘긴 값만 쓴다 (`STRUCTURED_NUMBERS_ONLY`, `STRUCTURED_VISA_CODE_ONLY`)
- **Eligibility 결과를 변경할 수 없다** (`ELIGIBILITY_RESULT_IMMUTABLE`)
- 가입 승인·승인 확률·신용점수를 생성할 수 없다 (`NO_APPROVAL_PROBABILITY`, `NO_CREDIT_SCORE_INFERENCE`)
- 외국인이라는 이유만으로 불가 판정을 유추할 수 없다 (`NO_FOREIGNER_INELIGIBILITY_INFERENCE`)

이러한 **Guardrail 15종**이 모든 응답에 적용되고 응답에 함께 반환된다. AI Service 장애 시에는 결정론적 템플릿으로 자동 전환되며, **이때도 Rule Engine 판정은 그대로 유지**된다.

#### ③ 공식문서 RAG 질의응답

사용자가 상품에 대해 자유롭게 질문하면, **승인된 공식 문서만** 검색해 근거를 인용하며 답한다.

- 상품·Rule 메타데이터로 검색 범위를 필터링
- 검색된 근거가 없으면 답을 만들지 않고 "확인이 필요하다"고 답한다
- 답변에 인용 번호와 원문 링크·확인일을 함께 제시

**평가 결과** (48케이스 · 6개 언어 · 답변불가 6건 포함):

| 지표 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 인용 정확도 | 0.44 | **0.95** |
| 정밀도 | 0.40 | **0.79** |

#### ④ 창구 대사의 번역과 다듬기 — 제한적 사용

「창구 준비 패킷」의 대사는 **골격을 검수된 템플릿으로 고정**하고, 생성형 AI는 번역과 쉬운 말 다듬기만 담당한다.

창구에서 읽는 문장은 환각의 위험이 가장 큰 지점이다. 사용자가 금융기관에 잘못된 주장을 하게 되기 때문이다. 그래서 **Rule 추출 파이프라인과 동일하게, AI의 자유도를 의도적으로 제한**했다.

### 5-3. 전체 파이프라인

```
공식 Source 수집 (도메인 allowlist · SHA-256 Snapshot)
   ↓
[생성형 AI] 조건 후보 제안
   ↓
[결정론적 검증] 인용문·숫자·비자코드·값 형식 원문 대조
   ↓
[사람] Human Verification 승인
   ↓
[Rule Engine] 결정론적 판정 — 충족 / 미충족 / 은행확인 / 불명
   ↓
[RAG] 승인된 공식 근거 검색
   ↓
[생성형 AI] 쉬운 설명 · 번역 · 다음 행동 (Guardrail 15종)
   ↓
「창구 준비 패킷」
```

## 6. 기대 효과 및 확장 가능성

### 6-1. 해결하는 구체적 문제와 기대 효과

| 문제 | SSAFIN의 효과 |
| --- | --- |
| 서류 누락으로 인한 재방문 | 내 프로필 기준으로 **필요서류를 3분류**해 사전 제공. 헛걸음 감소 |
| 창구에서 대화 중단 | **은행원 예상 질문 + 답변 선택지**를 사전 번역. 대화 지속 가능 |
| 잘못된 기대로 인한 신청 실패 | 은행 확인이 필요한 항목을 **미리 분리**해 제시. 실패 사유를 사전에 인지 |
| 언어 장벽 | 판정 메시지·서류·절차·대사까지 6개 언어. 미번역 문자열 0 (자동 검증) |
| 잘못된 정보로 인한 피해 | 모든 판정에 **공식 원문 근거**. 근거 없는 조건은 생성하지 않음 |

### 6-2. 실질적 혜택

**금융 고객(외국인)**

- 방문 전에 **자기 상황에 맞는** 준비물과 절차를 모국어로 확인
- 창구에서 언어 때문에 절차가 중단되는 상황을 회피
- 확률이 아닌 **공식 조건**으로 판단하므로 잘못된 기대를 갖지 않음

**서비스 제공자(금융기관)**

- 창구 상담 시간 단축 — 고객이 준비된 상태로 방문
- 서류 미비 재방문 감소 → 영업점 처리 효율 개선
- 통역 인력 의존도 완화 — **일요영업점 등 특화점포 투자 대비 효과 제고**
- 상품 조건의 **공식 근거 추적 가능성** 확보 — 불완전판매 위험 완화

앞서 본 대로 금융권은 이미 특화점포와 전용 플랫폼에 상당한 투자를 하고 있다. SSAFIN은 그 투자와 경쟁하는 것이 아니라, **고객이 그 창구에 도달했을 때 실제로 거래를 완결하도록** 돕는다.

### 6-3. 확장 가능성

**① 금융 서비스 내 확장**

- 등록 상품 확대 — 문서 수집 자동화(은행별 HTML 추출기, PDF 페이지 보존, 정기 수집 스케줄러)로 검수 속도 향상
- 변경 감지 후 재검수 워크플로 — 이미 SHA-256 해시로 원문 변경을 감지하고 사용자에게 표시하는 기능이 구현되어 있다
- 금융기관 제휴 시 창구 태블릿에서 패킷을 즉시 조회하는 형태로 확장

**② 대상 확장 — 디지털 격차 계층**

「창구 준비 패킷」의 구조는 외국인에게만 유효한 것이 아니다.

- **고령층**: 언어 번역을 **큰 글씨·쉬운 말 변환**으로 치환하면 그대로 적용된다. 창구에서 무엇을 말해야 하는지 모르는 문제는 동일하다
- **장애인**: 청각장애인에게 「은행원이 물어볼 말」 목록은 **필담 대체 수단**이 된다. 화면 낭독 지원과 결합하면 시각장애인에게도 적용 가능
- 세 집단 모두 **"제도는 있는데 창구에서 실행하지 못하는"** 동일한 구조의 문제를 겪는다

**③ 금융 외 영역**

공식 자료 → AI 제안 → 원문 대조 검증 → 사람 승인 → 규칙 판정이라는 구조는 **근거가 중요하고 오답의 비용이 큰 모든 행정 영역**에 적용된다.

- 출입국·체류자격 행정 (비자 연장, 체류자격 변경)
- 건강보험·국민연금 가입 안내
- 공공 임대주택 신청 자격
- 근로계약·산업재해 관련 안내
